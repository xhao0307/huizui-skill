# 怎样验证语料增强有没有用

状态：**比较方案已准备；三组独立运行和盲评尚未执行。** 作者试写不计为本方案结果。

## 同条件的三组

- A：同一模型，只给下方原生提示词和测试输入。
- B：同一模型，加载 `3de7e84` 版本的 `SKILL.md` 及其全部引用材料，再给同一输入。
- C：同一模型，加载当前技能及其全部引用材料，再给同一输入。

原生提示词应当足够强，不能故意设置一个弱基线：

```text
根据这段虚构对话，给出冷脸直怼、贴吧阴阳、精准拆招、更冲一点、一句收尾五种不同回复。简短、尖锐、自然，像真实聊天；不要写成讲道理的分析。贴合实际说过的话和已经给出的事实，不捏造背景，不混淆说话者，不拿正常批评当攻击。用户有具体错误时承认错误，不接受无根据的扩大化羞辱。不使用威胁、私密信息、亲属生死或群体歧视作为素材。每种优先一句，由使用者选择。
```

保持模型版本、采样设置和输入一致，每个样本使用全新会话。B、C 的参考材料加载方法保持一致；不得只给 B 一个入口却给 C 全套示例。记录实际使用的文件版本与上下文长度，避免把字数增加直接归因于语料来源。

## 样本怎么选

这里的案例卡与迁移试写已经被作者看过，属于开发材料，**不能再称作未见过的测试集**。独立评测时另写至少 20 组全新虚构场景，每组一正一反：只改变一项关键事实，原来的回击就应失效。

建议覆盖：

- 自己没有参与，与自己有明确贡献；
- 没有读过，与读过并指出具体错误；
- 同一人的双重标准，与不同职责造成的合理区别；
- 原词确能反照对方，与只是有相同关键词；
- 有确认回执，与仅有单方发送记录；
- 无论怎么回答都被定罪，与正常的具体追问；
- 用户被无端贬低，与用户确有待解决的错误；
- 多人说话与单人自相矛盾。

对比时打乱 A/B/C 标签。最好由未参与写技能的人判断，并分别记录“本人想选哪条”和“旁观者看哪条更贴合”；不能假装代表所有使用者。

## 判什么

先判事实错误：捏造记录、弄错对象、否认已知错误或反扣与输入相反的事实，记为失败，不能靠笑点分补回来。再对没有这些问题的输出比较：

| 维度 | 看什么 |
| --- | --- |
| 针对性 | 是否抓住此处独有的词、行动或矛盾；删掉背景后是否仍是万能骂法 |
| 口语感 | 能否直接说出口，是否像论文、客服或硬凑的金句 |
| 转折与力度 | 是否有具体刺点，是否需要解释才懂；不拿脏字数量当力度 |
| 选择差异 | 五条是否真正不同，是否包含可独立结束一轮的回复 |
| 事实敏感性 | 关键事实变了，输出是否跟着改变，还是继续套原来的指控 |

可按 0–2 分分别记录，但保留逐条理由，不只报一个总分。额外记录每组首选、平局与全部不想选。公开结果时同时给出样本量、模型版本、评审人数、失败例子和原始虚构输入。

如果 C 只让语言更花哨，却增加捏造或对正常批评的攻击，就不能称为改进。若想归因到案例卡，可再比较“新版只加载机制卡”与“新版加载机制卡和案例卡”；这也是待做实验，不是本轮已有发现。
